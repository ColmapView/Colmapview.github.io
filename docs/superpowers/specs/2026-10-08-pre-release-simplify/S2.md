## S2-4: One overlay-ownership rule for Spark and WebGPU
- **Where:** `SplatLayer.tsx:237-243` and `WebGpuSplatCanvasLayer.tsx:122-128`. Both were added by 674fa9c.
- **Change:** Move the duplicated predicate into `src/utils/splatLoadingProgressPolicy.ts`, which both renderers already import:
  ```ts
  export interface SplatLoadAttempt { file: File; startedDuringDatasetLoad: boolean }
  /** A tile download, or a dataset load that began after this splat's attempt began, owns the overlay, progress and URL error. */
  export function splatAttemptYieldsLoadingState(file: File, attempt: SplatLoadAttempt | null,
    isSplatDownloadPending?: () => boolean, isDatasetLoadPending?: () => boolean): boolean {
    return Boolean(isSplatDownloadPending?.())
      || (Boolean(isDatasetLoadPending?.()) && !(attempt?.file === file && attempt.startedDuringDatasetLoad));
  }
  ```
  - Each layer's `yieldsLoadingState` becomes a call to it, with `loadingNotificationRef.current` or `attemptRef.current`.
  - Spark's `SplatLoadingNotification` (`SplatLayer.tsx:45-50`) extends `SplatLoadAttempt`, and WebGPU's `attemptRef` (`:119`) is typed with it.
- **Why simpler:** The ruling "overlay ownership is decided by when an attempt started" gets one implementation, one comment and one name instead of two copies. Net about −4 lines.
- **Evidence:**
  - The expressions are identical apart from WebGPU's optional props. `Boolean(f?.())` equals `f()` for Spark's required callbacks.
  - Passing the functions keeps short-circuit evaluation exactly as it is.
  - The ref is still read when called, so Spark's `clearSplatLoadingNotification` still evaluates the rule before it nulls the ref (`:251-253`).
- **Risk:** Low.
- **Tests:** These must pass unchanged:
  - `SplatLayer.test.tsx:649`, `:891`, `:907`, `:922`, `:991` and `:1007`;
  - `WebGpuSplatCanvasLayer.test.tsx:2039-2115`.
  - Optionally add a 4-case unit test of the pure rule.
- **Note for code-review (not part of this change):** Spark's start writes the overlay without asking the rule (`SplatLayer.tsx:269-277`), while WebGPU's start does ask (`:159-165`), and the test at `:2115` pins WebGPU's behaviour. A WebGPU→Spark fallback during a tile download could briefly retake that download's overlay. Aligning the two would change behaviour, so it is not proposed here.
- **Size:** S. **Recommend.**

## S2-8: X11(c), the four Reload entry points: refuted, with one leftover wrapper
- **The four:**
  - `globalContextMenuActionExecutor.ts:285-289` awaits the reload, and the menu closes only after it (`useGlobalContextMenuActionExecutor.ts:18-24`).
  - `transformGizmoContextMenuExecutor.ts:23-27` does not await the reload, and closes the menu after the confirmation (`:36`).
  - `ExportPanel.tsx:201-205`.
  - `TransformPanel.tsx:63-66`.
- **Verdict:**
  - Each one is now `if (files && await confirmReload()) reloadFiles(files)` over two shared functions: `confirmReload` (`sessionActions.ts:59-68`) and `reloadFiles` (`useFileDropzone.ts:142-149`).
  - A helper would save about one line per site. Because the await differs observably, it would either change when the global menu closes or need a flag.
  - The earlier drift was real: TransformPanel reloaded without confirming. Four commits in this range edited all four sites in lockstep (2db2055, 973fa7f, b964311, 514e448), so they are consistent now.
- **Leftover, a needless indirection:** `useGlobalContextMenuActionStoreFacade.ts:58-61` wraps `reloadFiles` in `useCallback(async files => { await reloadDatasetFiles(files); })`. The only purpose is to turn `Promise<boolean>` into the dependency type `MaybePromise<void>` (`globalContextMenuActionExecutor.ts:120`). 5af7c3a added it in this range; at `v0.15.4` the function was passed directly.
  ```diff
  -  reloadFiles: (files: Map<string, File>) => MaybePromise<void>;
  +  reloadFiles: (files: Map<string, File>) => MaybePromise<unknown>;
  -  const { reloadFiles: reloadDatasetFiles } = useFileDropzone();
  -  const reloadFiles = useCallback(async (files: Map<string, File>) => {
  -    await reloadDatasetFiles(files);
  -  }, [reloadDatasetFiles]);
  +  const { reloadFiles } = useFileDropzone();
  ```
  - This is how `useTransformGizmoStoreFacade.ts:39` and `:52` already pass it.
  - The executor still awaits the same reload. Only one wrapper microtask goes, which nobody can observe.
- **Risk:** Low.
- **Tests:** `useGlobalContextMenuActionStoreFacade.test.ts:55-62` and `globalContextMenuActionExecutor.test.ts:226-241` stay unchanged.
- **Size:** S. **Optional.**
- **Observation, not proposed:** If the global menu and the gizmo menu should close at the same moment, one `reloadDataset()` could replace all four sites. That changes behaviour, so it is the owner's call.
